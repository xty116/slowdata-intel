# 「慢数据」情报 Agent —— AI 产品经理面试介绍框架

> 使用说明：本文档是"你"（项目作者，面试 AI 产品经理）的面试脚本。
> 讲法分三档：**30 秒电梯版**（§一）→ **3 分钟标准版**（§一~§六）→ **深聊版**（§七~§九，面试官追问）。
> 所有数字、案例均为本项目真实运行数据，可直接引用。

## 一、概述项目（30 秒电梯陈述）

**一句话**：我为一个 10 人规模的大模型数据团队，从零做了一个「慢数据」情报 Agent——每天自动扫描全网，产出带证据链的中文情报日报，并把所有线索沉淀成可检索的数据资产，把团队从"算法提需后才被动找数据"变成"数据提前就绪"。

**四要素拆解**：

| 要素 | 内容 |
|------|------|
| **人群** | 大模型公司/实验室的**数据团队**（负责找 benchmark 优质数据供应商并定向采买，服务对象是算法团队） |
| **场景** | 日常跟踪四类情报：① 最新 benchmark 与榜单变化 ② 竞品模型动态 ③ 竞品新招人才动向 ④ 数据供应商动作与数据采买线索 |
| **痛点** | ① **被动**：算法提需才找数据，交付滞后 2~3 周；② **分散**：信源横跨论文/公众号/开源社区/LinkedIn 等 500+ 来源，人工调研日均 2~3 小时；③ **无沉淀**：每次调研一次性，结论无法复用、趋势无法对比；④ **正确性无保障**：榜单口径冲突、旧闻当新闻，人工也会踩坑 |
| **方案** | LangGraph 编排的 13 节点日度流水线 + 模型分层（DeepSeek 官方 API）+ 多信源并行采集 + 证据核验与 Critic 回路 + SQLite 慢数据沉淀 + Web 看板，每日自动运行 |

**开场金句**（讲完四要素后收一句）："这个项目的本质不是'做一个爬虫 + 让 GPT 写日报'，而是把数据团队最核心的资产——**情报判断力——从人脑里的经验，变成带证据链、可复用、可追溯的数据资产**。"

## 二、全局分析并聚焦核心问题

> 面试官想听的不是"我做了啥"，而是"你怎么想问题的"。这一段是 PM 视角的分水岭。

**全局视角的三个追问**：

1. 用户的表层需求是"帮我每天搜最新情报"，但**为什么人工做不了**？——不是做不了，是边际成本恒定：每天 2~3 小时×人天成本，且换人即失忆（经验在脑子里）。
2. 团队真正缺的是"日报"吗？——不是。日报是表象，**缺的是"算法提需那一刻，储备库里有没有货"**。所以产品目标不是资讯推送，是**资产积累**（这就是"慢数据"的含义）。
3. 这类产品最大的风险是什么？——不是信息不全，是**信息错了**：数据采买决策动辄百万级，一条被污染的 benchmark 情报导致的错误采买，比没有情报更糟。

**提炼出三个核心矛盾**：

| 矛盾 | 表现 | 我的取舍 |
|------|------|----------|
| **广度 vs 成本** | 信息要覆盖 5 类信源，但 LLM 调用贵 | 模型分层：80% 环节用弱模型/零模型，单次运行 $0.13 |
| **速度 vs 正确性** | AI 分钟级产出，但会幻觉 | 不追求"不出错"，设计"错误可被检出→追溯→纠正"的闭环 |
| **一次性调研 vs 长期积累** | 团队要趋势判断，不是当天新闻 | 日报只是表象，SQLite 沉淀库（条目/断言/实体/事件）才是产品本体 |

**聚焦一句话**：*如何用可控成本，把每天全网情报变成"带证据、可追溯、可积累"的数据资产，让错误可被发现而不是被隐藏。*

## 三、方案对应问题（讲清 AI 介入的必要性）

**为什么必须 AI 介入**：量化人工不可行——500+ 信源、日均 2~3 小时调研（团队原话），且正确性校验（逐条搜证）人工做只会更慢。

**为什么不能"一个模型一把梭"**：团队之前的系统全链路用最强模型，成本高、且无法审计"哪句话是模型编的"。所以 AI 介入方式本身需要设计——我做了三件事：

1. **模型分层（成本分层即产品分层）**：

| 层级 | 承担节点 | 为什么用这层 |
|------|----------|--------------|
| L0 不用 LLM | 检索、抓取、去重、聚类、入库 | 确定性任务，用 LLM 是浪费且有幻觉风险 |
| L1 弱模型（deepseek-chat，温度 0 + JSON 模式） | 初筛分类、摘要、实体抽取、断言拆解/判定 | **答案空间封闭、模式固定**：四维分类、1~5 打分、三态判定，弱模型稳定且便宜 |
| L2 强模型（deepseek-reasoner） | 趋势综合、矛盾裁决、数据方针、Critic | **需要多步推理和权衡**：信源权威性×时效×表述精确度的裁决，评审能力必须高于生成能力 |

   效果：单次运行 **24~130 次调用、$0.036~0.14**，比全强模型低一个数量级；贵的模型只用在 5 个节点。

2. **正确性闭环（回答"AI 幻觉怎么办"）**：Claim 级核验（拆原子断言→逐条全网搜证→✅/❌/❓ 判定）→ 冲突时 L2 矛盾裁决（输出采信版本+置信度）→ Critic 五维评审 → 未达标自动回搜（≤2 轮，预算上限）→ 仍不达标就"降级接受并在报告显著标注"。**设计哲学：宁可诚实地说"时效性 4 分请人工复核"，也不假装达标。**

3. **业务规则代码化**：团队最核心的业务规则——"资料必须取提需时间前一周内、无日期条目不得作为唯一依据"——不只写在 Prompt 里，而是做成**四层硬过滤**（检索参数→入库过滤→初筛日期线索提取→抓页复核），Prompt 可以被绕过，代码不会。

## 四、分阶段落地

> 讲 PM 的分阶段逻辑：每阶段一个**可验证目标**、一个**验收标准**、一个**关键决策**。

| 阶段 | 目标 | 关键决策 | 验收标准 | 实际结果 |
|------|------|----------|----------|----------|
| **M1 MVP（先跑通闭环）** | 验证"AI 能否产出可用的日度情报" | 单信源（Tavily）+ 最小 9 节点流水线 + 日报 CLI；**不做核验不做看板**，先看天花板 | 跑出首份 Markdown 日报 | 1 天跑通：12 条 query→69 条→67 簇，成本 $0.036 |
| **M2 质量闭环** | 把"正确性"做成系统能力 | 时间窗硬约束、网页正文抓取（榜单页数据拿不到→JS 渲染兜底）、Claim 核验+矛盾裁决+Critic 回路+实体事件沉淀 | 证据链可点查 100%；被否结论不得出现在正文；Critic 低分必触发回搜 | 核验真实改变了结论：GPQA 榜单某模型得分被标 ❌，报告写明"不得传播原说法" |
| **M3 产品化** | 让非技术用户可用 | Web 看板（ECharts 可视化）+ 每日 08:30 定时 + 公网部署 + **公开只读/口令两种访问模式** | 浏览器可用、定时自动运行、公网可访问 | 团队打开即用，成本看板透明 |

**每个阶段都有"砍需求"的动作**（这是 PM 要主动讲的）：M1 砍掉多信源和核验，M2 砍掉深潜问答，M3 砍掉周复盘——先证明每一层假设，再堆能力。

## 五、结果与迭代

**量化结果**（可直接报数）：

| 指标 | 数值 |
|------|------|
| 效率 | 人工调研 2~3 小时/天 → 全自动流水线 2~8 分钟 + 人工复核 ~15 分钟 |
| 成本 | 单次运行 LLM $0.036~0.14（分层后为全强模型的 1/10 以下） |
| 沉淀 | 数日运行积累：400+ 条目、100+ 断言核验、100+ 实体、90+ 事件；跨天去重生效（同条新闻第二天自动标"复现"） |
| 质量透明化 | Critic 五维评分可视化；时效性低分如实展示 + 风险标注 |

**四个 badcase 驱动的迭代案例**（面试官最爱听"你怎么发现问题并改的"）：

1. **旧闻混入**（2024 年的文章出现在"今日情报"里）→ 不是模型幻觉，是**时间窗规则缺失** → 加日期线索提取层，单轮过滤掉 20 条超窗资料；
2. **榜单口径冲突**（用户说 SWE-bench 第一是 Muse Spark 1.1，系统抓到的榜单显示是 Claude Opus 5）→ 发现榜单页是 JS 渲染、正文抓不到 → 加 r.jina.ai 渲染代理兜底 + 矛盾裁决节点，让报告给出"带链接的证据 + 置信度"而不是拍脑袋；
3. **arXiv 官方 API 拦截 Python 客户端**（TLS 指纹，curl 能通 httpx 不通）→ 换 OpenAlex 论文源，同时印证了"信源冗余"设计；
4. **Critic 时效性持续低分** → 排查后确认是数据源客观限制（全网大量信源不暴露日期）→ 产品决策：把"时间未知"显式标注为特性（不得作为唯一依据），而不是调低门槛自欺。

## 六、认知成长（PM 视角的沉淀）

1. **模型分层是成本设计，更是产品设计**："哪些环节不用 AI、哪些用弱模型、哪些用强模型"这个决策表，本身就是产品的核心架构；
2. **AI 产品的正确性靠"可追溯 + 可降级"，不靠"保证不出错"**：Critic 打 4 分但如实标注，比强行达标更可信，也更安全（数据采买决策的代价锚定了这个选择）；
3. **业务规则要代码化，不要只 Prompt 化**：时间窗、双源原则这类规则写在代码里才兜底得住；
4. **合规是产品边界而非障碍**：LinkedIn/公众号没有合规 API，就设计出"定向检索 + CSV 导入"通道——约束反过来定义了产品形态；
5. **从"做功能"到"做资产"**：日报是表象，沉淀库才是护城河——"慢数据"是团队战略，不是功能列表。

## 七、面试官必问①：Agent 流程设计

> 按"输入 → Prompt 处理 → 输出"三段讲，逐节点说清"怎么理解、怎么执行、输出什么"。

### 输入（何时触发、接收什么）

- **触发**：定时（每日 08:30 北京时间）+ 手动（CLI / 看板按钮，本地可触发）+ 未来深潜模式（on-demand 提问，M4 规划）；
- **接收三样东西**：① **Watchlist**（关注主题与检索词清单——业务知识的载体，团队改清单即改产品行为，不需要改代码）；② **历史沉淀库**（近 7 天条目向量——让每天不是从零开始，重复新闻自动识别）；③ 日期（决定时间窗起点）。

### Prompt 处理（逐节点：怎么理解 → 怎么执行 → 输出什么）

| 节点 | 理解 | 执行 | 输出 |
|------|------|------|------|
| 查询生成 | 把关注主题翻译成"今天值得搜的问题" | L0 词表展开 + L2 生成 ≤4 条热点探测 query | 10~14 条检索 query（中英混合） |
| 并行收集 | — | L0：Tavily/OpenAlex/GitHub/HF/RSS 五路异步 + 时间窗第一层 | 归一化条目（标题/正文/URL/信源/日期） |
| 初筛 | 判断"相不相关、归哪个维度、多重要、是不是旧闻" | L1 批量 JSON：四维打标+重要度 1~5+日期线索提取（第二层过滤） | 每条目：relevant/dimensions/importance/date_hint |
| 正文抓取 | 搜索摘要不够，要页面里的真实数据（如榜单分数） | L0：抓正文+表格转文本+内嵌 JSON，JS 页面走渲染代理；页面日期复核（第三层） | page_text + 页面日期 |
| 去重 | 哪些是同一条新闻 | L0：本地嵌入聚类 + 跨 7 天向量比对 | 事件簇（带"新/复现"标记） |
| 摘要+实体 | 这个簇在说什么、涉及谁 | L1：2~3 句客观摘要 + 类型化实体 | summary + entities（company/model/benchmark/...） |
| **Claim 核验** | 哪些说法需要证明 | L1 拆 2~3 条原子断言 → 每条独立搜证 → L1 判定 | ✅证实 / ❌冲突 / ❓未证实（每条带证据链接） |
| **矛盾裁决** | 信源打架了信谁 | L2 权衡权威性×时效×精确度 | 采信版本 + 置信度（0~1） |
| 事件提取 | 发生了什么值得记入时间线 | L1 归一化事件类型 | events（发布/榜单动作/招聘/采买/融资...） |
| 趋势综合 | 今天整体发生了什么 | L2：带核验标记和日期的线索 → 四维度情报 | 情报正文（**硬规则**：推断必须标"(推断)"，未证实标"未证实"，被否结论禁止传播） |
| 数据方针 | 情报怎么变成动作 | L2：翻译成采买/储备建议 | P0/P1/P2 动作表（每行带依据编号）+ Watchlist 建议 |
| **Critic** | 这份报告合格吗 | L2 五维打分（事实性/完整性/引用可靠性/时效性/可操作性，0~10） | 分数+问题清单；任一 <7 → 生成补充 query 回搜（≤2 轮） |
| 回搜 | Critic 指哪补哪 | L0+L1：定向检索→重去重→重综合→再评审 | 增量证据；仍不达标 → 降级接受+⚠️标注 |

### 输出要求

- **日报固定结构**（9 段）：头部统计 / 情报正文（Top5+四维度） / 数据方针 / 证据核验与裁决 / 实体事件 / Critic 评分 / 线索附录 / 运行统计；
- **三条硬性输出规范**：① 每条结论强制带依据编号，可追溯到 URL+信源+日期；② 事实与推断物理分离（推断必须显式标注）；③ 附录每条线索标注核验状态（✅/❌/❓）与"时间未知"徽标；
- 同步写入 SQLite 六表（items/claims/entities/events/item_entities/runs）——日报是给人看的，沉淀库是给未来算法提需时查的。

## 八、面试官必问②：评测体系（四步走）

### 第一步：确定评测范围

评两个对象：**信息质量**（五维）+ **工程指标**（成本/耗时/信源可用率）。

- 信息质量五维：事实性（结论是否有证据支撑）、完整性（四维度是否覆盖）、引用可靠性（信源是否一手权威）、**时效性**（依据是否都在提需时间前一周内、是否误用时间未知条目）、可操作性（方针是否具体可执行）；
- 工程指标：单次成本（$0.13）、耗时、各信源命中率/失败率；
- 谁评：**Critic（L2 强模型）+ 人工抽检 + 客观规则硬指标**（时间窗过滤数、核验通过率这类数字不需要模型评，直接代码统计）。

### 第二步：怎么标注（标注标准书）

我们的"标注标准书"就是三份 rubric，全部版本化在 `config/prompts/` 里、可回滚：

1. **Critic 五维 rubric**：每个维度定义 0~10 分的含义（例：时效性 7 分=结论依据全部在窗内且无时间未知条目作唯一依据；4 分=多条核心结论依赖时间未知/超窗条目）；
2. **核验三态判定标准**：support=至少一条独立证据直接证实核心事实；contradict=证据与断言核心事实直接冲突；unverified=证据不足/仅间接提及；
3. **时间窗与日期规则**：默认前 7 天、无日期条目不得作为唯一依据、重要度上限 4。

**关键 PM 动作**：把"人写的评测标准"翻译成"模型可执行的 Prompt + 人可复核的清单"——同一个标准既是给模型的指令，也是给人抽检时的打分表，保证人机口径一致。

### 第三步：上线前后验收标准

- **上线前（M2 验收）**：核验过的断言证据可点查率 100%；被 ❌ 的结论不得出现在报告正文（人工抽查）；Critic 低分必触发回搜回路；单次成本 ≤ 预算（$0.5/日上限，超 60% 自动降级）；
- **上线后（持续观测）**：事实性/可操作性稳定 ≥7；时效性低分必须伴随"哪些条目导致的"清单（允许低分，不允许无解释）；零合规事故（不爬私有接口、密钥不进仓库）；效率指标 2~3h → ~20min 达成；
- **负向验收**（面试加分点）：故意投喂冲突信息，验证矛盾裁决是否触发、是否输出置信度。

### 第四步：bad case 分析优化（区分三类问题）

| 问题类型 | 本项目真实案例 | 修复动作 |
|----------|----------------|----------|
| **模型问题（幻觉/误判）** | 摘要引入原文没有的细节；断言判定误标 | 摘要输入强制绑定原文截断；温度 0 + JSON 模式；判定失败走"保守保留+未证实"降级 |
| **流程/工具问题（模型没错，系统没兜住）** | 2024 旧闻混入（时间窗规则缺失）；JS 榜单页抓不到数据（抓取能力不足） | 加日期线索提取层、渲染代理兜底——**这类占 badcase 大头，且修起来最快** |
| **人工/标注问题** | Watchlist 查询词过宽引入噪声；维度分类标准模糊 | 收紧查询词与 rubric 定义；标注标准版本化后先小样本试标 |

**迭代机制**：每次运行全链路可审计（节点级 token/成本/告警入库）→ badcase 归因到具体节点 → 修 Prompt 或规则 → 版本化发布 → 用下一轮运行验证。周复盘 Agent（M4 规划）将把这个循环半自动化（建议由人确认后应用）。

## 九、可能的追问清单（12 个 + 答题要点）

1. **"为什么用 LangGraph 而不是直接写脚本？"** → 13 节点状态流转 + Critic 条件回路（回搜≤2 轮）需要显式的图结构；检查点可断点续跑；未来深潜模式的 Supervisor-Worker 子图可复用节点。
2. **"为什么有些节点用弱模型？判断依据是什么？"** → 答案空间是否封闭（分类/打分/三态判定=封闭→弱模型）+ 是否需要多步推理（裁决/综合/评审=需要→强模型）+ 失败代价（初筛错了还有后面兜底，方针错了直接影响采买）。
3. **"怎么防止模型编造证据？"** → 三层：输出强制带依据编号且编号必须对应真实条目（渲染时校验）；断言核验独立搜证并留存 URL；Critic 事实性维度打分兜底。
4. **"时效性怎么保证的？"** → 四层硬过滤 + 无日期降权 + Critic 时效性维度，且这是团队提出的硬性业务需求，做成了代码规则而非 Prompt 约束。
5. **"如果信源都搜不到怎么办？"** → 降级链路：检索失败→空结果→维度写"今日无显著信号"；信源失败只告警不中断；渲染代理兜底 JS 页面。
6. **"成本怎么控的？"** → 三层：模型分层（大头）、预算上限+自动降级（L2→L1）、节点级配额（核验簇数/摘要簇数/Tavily 用 basic 档）。
7. **"为什么做 Web 看板而不是只发个日报？"** → 日报解决"读"，沉淀库解决"查"；看板把沉淀库变成可视资产（实体时间线/条目检索），是"慢数据"产品化的关键一步；成本透明化让团队信任 AI 运行。
8. **"公网部署的安全考虑？"** → 公开只读模式（禁止触发付费运行/改配置）+ 口令模式二选一；密钥不入仓库不入镜像（环境变量注入）；看板输入全部转义防注入。
9. **"这个系统会取代数据团队的人吗？"** → 定位是"把人从检索搬到决策"：AI 负责广度与初筛，人负责采买决策与复核（报告末尾明示"重要决策请人工复核原文"）。
10. **"如果让你重做，会改什么？"** → 先做评测后做功能（M1 就埋 Critic 埋点）；向量库从第一天就考虑扩展（当前 10 万级暴力检索够用，但接口已预留）；实体别名归一提前做。
11. **"怎么衡量这个项目成功？"** → 三层：效率（调研时长下降）、资产（储备库命中率——算法提需时库里有多少能直接调用的线索）、决策质量（采买决策的依据是否带证据链）。
12. **"Agent 和传统爬虫+报表的区别？"** → 爬虫只解决"收集"，Agent 解决"判断+闭环"：分类判断、证据核验、矛盾裁决、质量评审、自动回搜——这些是传统 pipeline 没有的"认知层"；且输入是 Watchlist 而非硬编码 URL，行为可被业务团队直接调整。
